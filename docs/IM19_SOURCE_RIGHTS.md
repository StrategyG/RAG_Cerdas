# IM19 source rights review procedure

## Purpose

Operational access permission and legal/contractual rights are separate decisions.

- access_authorized means an authorized operator permits IM19 to access/process the file.
- source_rights_reviews records whether the exact source revision/hash may be stored and embedded under a documented rights basis.

The current PDF/EPUB pipeline stores extracted page/chunk text and embeddings. Therefore a source may be approved for this pipeline only when both storage_allowed and embedding_allowed are true. derivative_notes_allowed is recorded for future notes-only workflows; it does not enable one today.

## Required human review

For every exact source revision:

1. Confirm source identity, owner, source URI, revision, and content hash.
2. Review the exact license, terms, owner attestation, public-domain basis, or written permission.
3. Confirm intended internal storage, extraction, and embedding are permitted.
4. Record attribution and a durable evidence reference.
5. Approve, hold, or reject with a rationale.
6. Re-review after a new revision or content hash. The newest decision for the exact revision/hash controls.

Do not infer rights from Dropbox possession, public availability, repository visibility, or the fact that a file can be downloaded. Sources with unclear rights, no-RAG restrictions, or conflicting terms remain on hold. The MASTER_CONTEXT file, credentials, private messages, and unrelated personal-library material are excluded from product RAG.

## Controlled write path

Only a trusted human approver login that is a member of im19_approver can append rights decisions. The worker role has read-only access to the rights ledger. Review rows are append-only.

Example transaction for an approved source (replace the placeholders with values obtained from the approved review record):

    BEGIN;
    SET LOCAL ROLE im19_approver;

    INSERT INTO im19.source_rights_reviews (
      source_file_id, revision, content_hash, decision, rights_basis,
      license_identifier, attribution, evidence_reference, rationale,
      storage_allowed, embedding_allowed, derivative_notes_allowed, reviewer_id
    )
    SELECT
      f.id, f.revision, f.content_hash, 'approve', 'owner_attestation',
      NULL, 'Attribution text required by the source owner',
      'Rights evidence reference or reviewed terms URL',
      'Rationale and scope of approval',
      true, true, false, 'reviewer-identifier'
    FROM im19.source_files AS f
    WHERE f.id = 'SOURCE_FILE_UUID';

    COMMIT;

This example is a controlled operator procedure, not an automated worker action. Use the actual reviewed rights basis and attribution; do not copy the example values as real approvals.

## Resume behavior

The worker resumes a source blocked for rights/access only after:

- the latest exact-revision/hash rights decision is approve,
- storage_allowed=true,
- embedding_allowed=true, and
- source_files.access_authorized=true.

A rejected/held decision, a stale revision, or missing evidence does not resume the job. The worker rechecks exact-version rights before download, parsing, mining/review, and embedding; persistence methods recheck inside their database transactions. The database publication trigger repeats the rights check against the exact document_versions revision/hash. A later hold/reject quarantines an already-published exact version and removes it from retrieval.

## Evidence limits

The migration restricts INSERT to im19_approver, but reviewer_id is an operator-supplied value and is not authenticated by this migration. Production must use unique named approver logins and map session_user to an authoritative reviewer registry and immutable audit record; a free-form reviewer_id is not identity proof.

A later hold/reject quarantines an already-published exact version so retrieval no longer serves it. **Quarantine is not erasure**: existing page/chunk/knowledge/embedding rows and downloaded local blobs may remain. A reviewed purge/retention workflow is not implemented. Production remains blocked for any source requiring withdrawal or erasure until that workflow is approved, implemented, and tested.

The migration and local tests validate role separation and state gates in disposable PostgreSQL. They do not constitute legal advice or a legal determination for any source. A source owner or authorized rights reviewer remains accountable for the decision. No rights review is automatically generated by AI.
